# Frontend spec — CRM / Inbox del agente (web)

> Front del CRM que opera el staff de Mirko. **Diseño canónico del agente: repo `server`** (`server/docs/FLUJO_AGENTE.md`, `DESIGN_AGENT_ARCHITECTURE.md`, `SPECS_MVP.md`). Este doc cubre las piezas de **frontend**.
> Stack: Next.js 16 App Router · Tailwind v4 · shadcn · Zustand · React Query · Axios · Zod (ver [CLAUDE.md](../CLAUDE.md)).

## Pantallas (en `/crm`)

1. **Inbox de conversaciones** — lista (contacto, último mensaje, etapa del funnel, **badge 🔥 cuando `handed_off`**) + panel de hilo con burbujas. Reutilizable: burbujas de chat de Firefly-App (`conversation-message.tsx`).
2. **Takeover** — toggle **IA on/off** por conversación (`is_ai_active`). Con IA on, el input se deshabilita; con IA off (humano tomó), el humano escribe por el hilo (envío vía backend → Meta). El composer además permite **adjuntar imagen/PDF** (clip, drag & drop sobre el hilo, o paste; JPG/PNG/PDF ≤5 MB, el texto acompaña como caption) y **enviar el QR de pago** del sistema con un botón dedicado (#169, server#251).
3. **Pipeline "Gestión Postventa"** (kanban, `kind: 'human'`; "Gestión Humana" hasta el rename de 2026-08-30, server 0035) — los leads derivados (handoff) entran acá. Stages: `Por atender → Por validar pago → Pago validado → Entregado → Cerrado` → [Fase 2] `Asistió / No asistió / Lost`. Acción **`/generarEntrada`** (dispara al backend) desde la card al validar el pago; el backend la acepta **solo si el servicio aceptado es presencial** y devuelve el motivo en el `detail` del error si no. Los nombres de stage llegan del backend: el front no compara por string (usa `status_code` para won/lost).
4. **Config del agente (ABM) — solo `platform_operator` (Natalia + equipo):** editar system prompt (textarea), nivel de emojis (switch mucho/poco/nada), temperatura (slider); guardar crea `agent_version`. **Mirko (`client_admin`) y el staff NO** ven esta pantalla.
5. **Entradas — control de acceso en la puerta** (`/entradas`, CR6, web#185 / server#278): pantalla **móvil, sin guarda de rol** (quien atiende la puerta suele ser `staff`). Se elige el evento que se está controlando y se leen los QR con la cámara: el veredicto ocupa la pantalla (verde = pasa, ámbar = `legacy` "pasa, verificá", rojo = rechazo) con el `detail` del backend **tal cual** más nombre, curso y monto. La **lista de asistencia** con búsqueda por nombre y **check-in a mano** es el camino de escape cuando la cámara no sirve: sin ella un permiso denegado dejaría afuera a alguien que pagó. Componentes en `components/crm/entries/`.

## RBAC (front) — 3 niveles

> **Actualizado 2026-07-22** (split #126, server #200; anula "admin = Mirko" de 2026-06-06). Modelo canónico: `server/docs/SPECS_MVP.md` §RBAC.

- **`platform_operator`** (Natalia + equipo, p. ej. Chris): ve **todo**, incl. config del agente, users/roles de cualquier tenant, settings.
- **`client_admin`** (Mirko): operación de su organización — inbox + tablero CRM + sus leads + catálogo — **+ gestión de su propio staff** (`/crm/users`: alta/baja/cambio de rol `client_admin`↔`staff`; sin tocar operadores). **NO** config de plataforma, **NO** edición del agente.
- **`staff`** (la hermana): inbox + pipeline Gestión Postventa + takeover. **NO** config, **NO** usuarios.

Capacidades en `hooks/use-permissions.ts`: `canManageUsers` (operador ‖ client_admin) **separada** de `canManageConfig` (solo operador). Guardas de UI en la tabla de usuarios (espejo de la matriz backend): fila de operador sin selector de rol y sin acciones para client_admin; fila propia sin cambio de rol ni auto-baja. Guards de ruta + ocultar UI; el backend **revalida** (no confiar solo en el front).

## Realtime

- Mensajes nuevos (entrantes de Meta y respuestas del agente) aparecen sin recargar: el backend publica por **Redis Pub/Sub** → el front escucha por **WebSocket/SSE propio** (NO socket.io de terceros). Hasta integrar, mockear con polling.

## Contratos que consume (del backend — ver `server/docs/SPECS_MVP.md`)

- API de conversaciones/mensajes · toggle `is_ai_active` · `GET/PUT /api/v1/agents/{id}/config` (admin-only) · endpoint que dispara `/generarEntrada`.
- **Entrega post-pago (CR1, web#178 / server#268):** el servicio del catálogo agrega `modality` (`presencial` | `virtual` | `null` = sin entrega) y `price_amount` (monto comparable con el comprobante; `null` = validación manual) · links de entrega por servicio (`GET/POST /services/{id}/links`, `PUT/DELETE /service-links/{id}`, tope 5) · config de pagos por organización (`GET/PUT /crm/payment-settings`: beneficiario esperado + QR propio o global, `client_admin` ‖ `platform_operator`).
- **Comprobante de pago (CR3, web#182 / server#272):** `GET /crm/cards/{id}/receipt` devuelve el comprobante más reciente o **200 con body `null`** (no 404) · `POST /crm/cards/{id}/receipt/validate` valida **y entrega** en una operación (400 si el veredicto es `fail`) · `POST /crm/cards/{id}/receipt/override` hace lo mismo con `{ note }` obligatoria (≥3 caracteres tras normalizar espacios, 422 si no). El panel vive en el detalle de la card (`components/crm/receipt/`): imagen + datos extraídos **sin reformatear** + semáforo de checks. Los `code` de check son códigos (`price`, `currency`, `amount`, `beneficiary`, `date`, `reference`, `reused`, `media`) y el copy corto vive en `components/crm/receipt/labels.ts`; el `detail` ya viene en español del backend y **no se re-genera** en el front. Avisos nuevos en `flags`: `receipt_review`, `payment_unconfirmed`. **Estado del comprobante (web#194 / server#292):** el comprobante trae `approved_at` / `approved_by` (`'system'` o el uuid del operador; `null` si nadie lo aprobó; con default en el schema para un backend anterior). `receiptState()` (`lib/api/receipt.ts`) lo resuelve por precedencia `rejected` (`human_rejected_at`) > `confirmed` (`human_confirmed_at`) > `approved` (`approved_at`) > `pending` (checks en verde) | `review` (en rojo), y el panel (`receipt-status.tsx`) muestra "Rechazado" / "Confirmado contra el banco" / "Aprobado por el sistema" (con link a `/pagos` mientras falte el cotejo) / "Validado a mano" (con su nota) / "Las verificaciones cerraron" / "Necesita tu revisión". **Solo `pending` y `review` tienen acciones**: sobre un pago ya aprobado el backend responde 400 y, antes de server#292, ese botón retrocedía la card y re-entregaba al lead.
- **Modalidad de entrega (catálogo):** `modality` acepta `presencial` | `virtual` | `hibrido` | `null`. **`hibrido`** es presencial y virtual a la vez — entrada QR + ubicación + los links de la clase en un mismo mensaje — y existe porque el único servicio que se cobra por QR es un curso de 4 módulos con uno presencial y tres por Zoom: ninguna de las otras dos lo entrega completo. A diferencia de `virtual`, **nunca queda bloqueado**: si falta un link entrega la entrada igual y deja el aviso `missing_link`. El copy y las etiquetas viven en `components/crm/catalog/labels.ts`.
- **Puerta del evento (CR6, web#185 / server#278):** `POST /crm/entries/redeem` con `{ token, event_id? }` y `POST /crm/entries/{entry_id}/check-in` con `{ event_id? }` devuelven **el mismo shape** y **siempre 200** — un rechazo no es un error HTTP, porque en la puerta hace falta leer el motivo, no un status. `status` es un **código** (`ok`, `legacy`, `already_used`, `wrong_event`, `revoked`, `not_found`, `payment_qr`) y se parsea como `string`, nunca como enum: el color lo decide `admitted` (+ `legacy` → ámbar), así que un veredicto nuevo del backend se muestra igual. El `detail` ya viene redactado en español y **no se re-escribe ni se re-genera** en el front (mismo criterio que los checks del comprobante). `GET /crm/entries/attendance/{event_id}` devuelve `{ total, checked_in, attendees }`; incluye las entradas **anuladas** (`revoked_at`) a propósito y marca con `used_manually` a quien entró sin mostrar el QR. El token del QR **no** sale en la lista — es el secreto que valida la entrada —, y por eso el check-in va por `entry_id`. `GET /crm/agenda` (server#276) está **abierto a los 3 roles** desde server#281: quien atiende la puerta es `staff` y necesita elegir el evento, sin lo cual el rechazo por `wrong_event` sería inalcanzable. El ABM de eventos sigue cerrado a `client_admin`. La pantalla igual degrada ante un 403 (explica qué pedir y sigue escaneando) por si corre contra un backend viejo.
- **Conciliación de pagos (CR4, web#184 / server#274):** `GET /crm/payments/pending` → `{ total, items }` con solo los pagos que **el sistema** aprobó y nadie cotejó (los validados a mano no entran) · `POST /crm/payments/{id}/confirm` (sin body, idempotente) · `POST /crm/payments/{id}/reject` con `{ note }` obligatoria (≥3 caracteres tras normalizar espacios; 422 si no, 400 del dominio) → **revoca la entrada** y mueve la card al stage `lost` · `GET /crm/payments/export?day=YYYY-MM-DD` → CSV (`day` opcional, default **hoy en hora de Bolivia** desde server#281; los límites del día también son bolivianos, porque se coteja contra un extracto bancario local). Pantalla propia en `/pagos`, visible para los 3 roles, con el contador en el menú (`components/crm/payments/`). `amount`, `currency` y `paid_at` (date-only) se muestran **sin reformatear**, mismo criterio que el panel del comprobante.
- **Avisos de entrega (CR2, web#179 / server#270):** la card trae `flags: string[]` (default `[]`) en `/crm/boards`, `/crm/cards/{id}` y la respuesta de `move`. Son **códigos** (`needs_name`, `delivery_pending`, `extra_receipt`, `no_modality`, `missing_link`, `ambiguous_service`, y desde server#276/#290 `no_event` y `capacity_full`) y el copy en español vive en `components/crm/flag-badges.tsx`; un código desconocido se muestra crudo, nunca rompe el parse. **Catálogo vs agenda (web#192):** un servicio presencial o híbrido se vende desde el catálogo (`modality`, precio, links) y además necesita **un evento en `/agenda`** (fecha, lugar, cupo) para que la entrada salga; sin evento próximo la card queda con `no_event`, el lead ya recibió la confirmación del pago (server#290) y al guardar el evento la entrega sale sola. El form del servicio y la agenda lo explican con link cruzado. `card_move.moved_by` agrega el literal `'system'` (entrega y cierre automáticos) además de `'agent'` y el uuid del operador.
- **Errores del agente (web#190 / server#288):** el hilo puede traer mensajes con `sender: 'system'` y `type: 'error'` — el agente no pudo responder ese turno (fila `role: system` en `ai_chat_histories`, fuera de la ventana del LLM) — con `category` como **código** (`auth`, `rate_limit`, `bad_request`, `provider`, `network`, `internal`, `delivery`); el copy vive en `components/crm/agent-error-event.tsx` y un código desconocido se muestra crudo. Se renderiza como **chip centrado**, nunca como burbuja del agente. La card trae `alert: 'agent_error'` (mismo mecanismo que `unknown_service`) y el SSE suma `{ type: 'agent_error', conversation_id, category }` → invalidar board + card. Ante un fallo del proveedor la conversación deriva a Gestión Postventa y queda con **IA apagada hasta que el staff la reactive** (diseño, no bug). El catálogo de modelos trae `supports_temperature`: si el modelo elegido no la acepta, el form lo anota — el backend la omite solo.
